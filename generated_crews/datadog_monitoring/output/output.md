### 근본 원인 가설 (Preliminary Root Cause Hypotheses)

정상 운영 가능성과 관측 공백 가능성을 모두 고려한 가설을 우선순위별로 제시합니다.

**가설 A: 정상 운영 구간 (확률: 중)**
- 해당 서비스가 실제로 안정적으로 동작 중이며 지난 1시간 내 오류가 발생하지 않았음
- 검증 방법: `status:error` 조건을 제거하고 `service:erody-bo-backend-20`만으로 재조회하여 전체 로그량(볼륨) 확인 → 로그 자체가 정상적으로 유입되고 있는지 확인

**가설 B: 서비스 태그 매핑 불일치 (확률: 중~높음)**
- `erody-bo-backend-20`의 `-20` 부분이 실제 Datadog `service` 태그와 정확히 일치하지 않을 가능성 (예: env, version 태그로 별도 관리되는 경우)
- 검증 방법: Datadog APM/Service Catalog에서 정확한 서비스명 확인, 또는 `service:erody-bo-backend*` 와일드카드 쿼리로 재검색

**가설 C: 로그 인덱스/파이프라인 설정 이슈 (확률: 중)**
- Log Pipeline의 Grok 파싱 실패로 `status` 필드가 `error`로 정상 매핑되지 않았을 가능성
- 인덱스 Exclusion Filter에 의해 error 로그가 필터링되어 인덱싱되지 않았을 가능성
- 검증 방법: Datadog Log Pipeline 설정 및 Index Exclusion Filter 정책 검토, Live Tail로 실시간 로그 유입 여부 직접 확인

**가설 D: 인증/API 스코프 문제로 인한 부분 조회 (확률: 낮음)**
- API 응답 `status: "ok"`이므로 가능성은 낮으나, `DD_APP_KEY`의 권한 범위가 특정 인덱스나 서비스에 제한되어 있을 가능성
- 검증 방법: 다른 서비스명으로 동일 쿼리 테스트하여 API Key/App Key 권한 정상 여부 확인
